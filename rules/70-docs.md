# Документация

## Принцип
Документируй так, чтобы человек (или агент), открывший проект через полгода,
за 5 минут понял: что это, как запустить, как устроено. Не больше и не меньше:
устаревшая документация вреднее её отсутствия.

## README проекта — обязательный минимум
1. **Что это** — одно-два предложения: что делает и для кого.
2. **Стек** — язык, фреймворк, БД, ключевые библиотеки.
3. **Как запустить** — по шагам, с нуля, включая установку зависимостей
   и переменные окружения. Проверено: шаги реально работают.
4. **Как тестировать** — команда запуска тестов.
5. **Структура** — 5–10 строк: главные папки и что в них.

## Поддержка актуальности
- Изменил команды запуска, env-переменные, структуру — обнови README
  в том же коммите.
- `.env.example` всегда синхронизирован с реально используемыми переменными.
- AGENTS.md / CLAUDE.md обновляется, когда меняются команды или соглашения проекта.

## Решения
- Важные архитектурные решения фиксируй коротко (можно прямо в README
  или в `docs/decisions.md`): что решили, почему, какие были альтернативы.
  Одного абзаца достаточно. Через полгода «почему тут MongoDB?» будет иметь ответ.

## Чего НЕ делать
- Не документируй то, что видно из кода (пересказ функций строка за строкой).
- Не генерируй тома документации «для галочки» — их никто не читает,
  а поддерживать их дорого.
- Не оставляй в доках ссылок на несуществующие файлы и устаревшие команды.
