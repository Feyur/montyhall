# Стиль кода

## Главное правило
Код читают в десять раз чаще, чем пишут. Пиши для читателя.
Новый код не должен отличаться по стилю от существующего кода проекта.

## Именование
- Имена говорят, ЧТО это, без заглядывания внутрь: `activeUsers`, а не `data2`.
- Функции — глагол: `sendEmail`, `validateInput`. Булевы — вопрос: `isReady`, `hasAccess`.
- Никаких сокращений, кроме общепринятых (`id`, `url`, `db`).
  `usrMgrSvc` — плохо, `userService` — хорошо.
- Одно понятие — одно слово во всём проекте: не смешивай
  `fetch`/`get`/`load` для одного и того же действия.

## Комментарии
- Комментарий объясняет ПОЧЕМУ, а не ЧТО. Что делает код — видно из кода.
- Если код требует комментария «что происходит» — перепиши код понятнее.
- Уместны: неочевидные ограничения, обход бага в библиотеке, ссылка на спецификацию.
- Мёртвый код удаляется, а не комментируется — история есть в git.
- Никаких `TODO` без тикета/issue: либо сделай, либо зафиксируй где-то, где не потеряется.

## Функции
- Функция читается сверху вниз без прыжков. Ранний выход (guard clause)
  вместо вложенных `if`.
- Аргументов не больше 3–4; больше — передавай объект/структуру.
- Никаких скрытых сюрпризов: функция `getUser` не должна попутно
  что-то записывать или удалять.

## Форматирование
- Форматирование делает инструмент (prettier/black/gofmt/…), не человек.
  Настрой один раз — и не спорь со стилем руками.
- Линтер включён и чист. Предупреждения не игнорируются молча:
  либо исправь, либо явно подави с комментарием-причиной.

## Типы и данные
- В типизированных языках — типизируй честно: без `any`/`Object`,
  когда известен реальный тип.
- Не мутируй входные аргументы; возвращай новое значение.
- Данные валидируй на границе (ввод пользователя, ответ API), внутри — доверяй типам.
