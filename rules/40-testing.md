# Тесты и проверка

## Принцип
«Написал» ≠ «работает». Работа не закончена, пока изменение не проверено
в действии: код запущен, поведение увидено, тесты зелёные.

## Что тестировать в первую очередь
1. Бизнес-логику: расчёты, правила, преобразования данных.
2. Граничные случаи: пусто, ноль, отрицательное, очень много, не тот тип, юникод.
3. Обработку ошибок: сеть упала, файла нет, доступ запрещён.
4. Найденный баг: сначала тест, воспроизводящий баг, потом фикс.
   Так баг не вернётся.

Не гонись за процентом покрытия — гонись за покрытием того, что страшно сломать.

## Как писать тесты
- Тест проверяет ОДНУ вещь, имя описывает её:
  `test_discount_not_applied_to_empty_cart`.
- Структура: подготовка → действие → проверка (Arrange–Act–Assert).
- Тесты независимы: порядок запуска не важен, общего изменяемого состояния нет.
- Тест падает по понятной причине. Тест, который «иногда падает», —
  сломанный тест: чинить или удалять, а не перезапускать.
- Не тестируй чужой код (фреймворк, библиотеку) — тестируй свой.

## Проверка руками (обязательно, даже при зелёных тестах)
- Пройди изменённый сценарий как пользователь: от входа до результата.
- Для UI — посмотри глазами: вёрстка, состояния, консоль без ошибок.
- Для API — дерни эндпоинт реальным запросом, посмотри ответ.

## Перед завершением задачи
1. Все тесты проекта проходят (не только новые).
2. Линтер и сборка чистые.
3. Изменённый сценарий проверен вручную.
4. В отчёте написано, ЧТО и КАК проверено. «Должно работать» — не отчёт.
